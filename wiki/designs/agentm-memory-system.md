# AgentM Memory System

## Objective

Memory is the **durable record agentm keeps** — what it has learned, the plans and designs it works on, the standards it holds — and the single disciplined path every caller takes to reach it. It is the largest of the four pillars and the ground the other three stand on: **Experience** grows it, **Opinions** keep their learned half in it, **Personas** draw their state from it.

It is built to **compound**: entries are typed, densely linked to their neighbors, and indexed for recall — so as agentm learns and reaches outward, the record grows into an interconnected knowledge base.

## Overview

The substrate serves one aim: **every caller reaches storage the same way, and nothing leaks a dependency downward.** A small set of generic pieces — none knowing a specific backend, host, or tool — arranged so everything points *inward*: a caller reaches the memory engine, the engine reaches storage through the resolution plane and the seam, and the concrete backends, personas, and crickets tools all depend *up*. The substrate depends on nothing below it.

![Whole-component view: in-process callers, MCP clients (opt-in), crickets tools, and personas all depend on the memory engine; the engine reaches the resolution plane then the storage seam; the device-local and obsidian-vault backends implement the seam — every arrow points inward to the substrate](diagrams/agentm-memory-whole-component.svg)

The components:

- **The memory engine** — the verbs the rest of the system calls (`save` · `recall` · `forget`, plus reflection) and the cross-cutting logic that must live exactly once: idempotency + content-hash CAS, soft-delete, token-budgeted recall, link integrity.
- **The resolution plane** — how a call finds its store without naming one: the config holds the backend choice; the selector (`backend_selection.py`) maps a protocol name to a concrete `StorageBackend`, failing loud if it's missing.
- **The storage seam** — the one port to disk: a `StorageBackend` contract, a registry, an opaque `Locator`, and the storage tiers. *(The seam's full contract — the verbs, the `Locator` guards, the tiers + the never-sync invariant, the reserved `DerivedMaintenance` — is the launched [memory-storage-seam design](memory-storage-seam.md); this pillar points down to it.)*
- **Harness-state I/O** — plan/progress/feature state is backend-aware: it routes through the seam to the active backend, so state and memory reach disk the same way.

**The one-way rule, enforced.** Routing and memory code may import the seam + selector (substrate) but **never a concrete backend** — the LC-8 gate (`check-process-seam-import-direction.sh`) fails the build on any `import storage_vault`. The backend is chosen at call time and injected through the abstract contract. Backends and tools point up; the substrate points at nothing below.

## Design

### How memory is classified — three axes

agentm classifies every memory on **three independent axes**: by **kind** (what sort of thing it is), by **durability** (does it survive the session?), and by **ownership** (whose space is it?). Kind drives *retrieval*; durability and ownership drive *placement*.

**By kind.** Every entry declares a **`kind`** — open-ended but conventional: `preference` · `workflow` · `fix` · `domain-reference` · `idea` · `skill-pointer`. Kind is central: it picks the storage group an entry is written to, and it scopes which entries a phase pulls into its recall budget (a `/work` pass recalls different kinds than a `/plan` pass). Kind is how a caller asks for *the right sort of memory* rather than a flat search over everything.

**By durability + ownership.** Two planes:

- **Layer 0 — agent-harness memory (not durable):** the host's context window — the running conversation. Short-lived; it fills and gets summarized away. Scratch space; the record lives below, on disk. *(The layer the whole substrate exists to compensate for.)*
- **Layer 1 — the durable record (on disk):** resolved at runtime, never a cached path. It splits into **three ownership tiers, by ascending agent autonomy** — and each tier is a place in the vault:

| Tier | What it holds | Where | The agent's hand |
|---|---|---|---|
| **T1 — personal** | the operator's own notes | the Obsidian vault *above* `Agent/` (its siblings) | reads + links; **writes only when told**, through a separate seam call |
| **T2 — curated / collaborative** | designs · plans · roadmaps, and the operator-directives the agent follows (voice, conventions, preferences) | `Agent/desk/` — *our* shared working surface | writes as needed and **reports each change in the digest**; revertable |
| **T3 — agentm-sole** | the agent's own learned memory + insights | `Agent/memory/` | writes, curates, and prunes freely; no notice |

Personal (T1) sits *outside* agentm's `vault_path` (which is `Agent/`), so it is out of reach by default, not by policy alone. The agent writes there only through an **explicit, separate storage-seam call** that an operator request authorizes — keeping agent-controlled and user-controlled space cleanly apart (the [memory-storage-seam design](memory-storage-seam.md)). Autonomous jobs work mostly in T3; when a job changes T2, that change lands in the digest for the operator to see and revert.

### The vault layout

The structure is opinionated — the agent controls most of it, so the design fixes the shape.

Paths below are written against the two resolvers rather than any machine's
literal layout — `vault_path()` is the Obsidian vault and git root,
`memory_root()` is the agent's tree one level inside it. They are **not** the
same directory, and addressing the wrong one silently mis-roots every
vault-relative path (see the vault-path convention in `AGENTS.md`).

```
<vault_path>/                    T1 personal — the operator's vault; agentm does not touch it
├── Calendar/ · Personal/ · …      the operator's own folders and loose notes
└── Agent/  = <memory_root>      the agent's tree — everything below is agentm's
    ├── desk/                    T2 curated — the shared working surface
    │   ├── projects/<project>/    designs · plans (_harness) · roadmap · progress
    │   ├── projects/_global/      cross-project stores (e.g. wiki-style voice overlays)
    │   └── briefs/ · scratch/     short-lived working material
    ├── external/                  third-party sources the agent reads but never authors
    ├── _meta/                     device-local sidecars — health, caches, snapshots; derived, never synced as truth
    ├── _dream/                    dreaming output
    ├── _vault-archive/            retired curated content (cold; recall skips it)
    └── memory/                  T3 agentm-sole — the agent's own memory
        ├── _always-load/          the heat-promoted floor (flat — kind is not a subfolder here)
        ├── <kind>/<slug>.md       the leaf: kind is the subfolder (insight/, feedback/, workflow/, fix/, …)
        ├── <year>/<month>/        the dated subtree
        ├── _inbox/                raw reflection candidates (recall-excluded by default)
        ├── _watchlist/ · _opinions/   staged candidates and accumulated opinions
        ├── _idea-incubator/       agent-incubated ideas
        └── _archive/              the cold zone (recall skips it)
```

**T2 (curated) shape.** Curated content lives under `desk/projects/<project>/` — each project carrying `designs/`, plans in `_harness/`, a `roadmap`, and a `progress` log — alongside the shorter-lived `desk/briefs/` and `desk/scratch/`. No loose notes at the root. The operator-directives the agent follows (voice, conventions, preferences, feedback) are curated: the operator owns them, the agent refines them and reports the change. **Where those directives now sit is an open question** — the four-space migration moved them under `memory/`, which this design labels T3, so either the paths or the tier boundary need an owner's ruling; the amendment log records it rather than guessing.

**T3 (memory) leaves** reuse the live entry convention — `<kind>/<slug>.md` with the locked frontmatter (below); **kind is the subfolder**, because kind drives recall. The reserved leading-underscore folders (`_always-load`, `_inbox`, `_archive`, `_idea-incubator`, `_watchlist`, `_opinions`) are recall-aware. `_meta/` is **not** among them any more — it sits at the `Agent/` root beside `memory/`, since device-local sidecars are derived state for the whole tree rather than memory leaves. `crystallized/` now serves two writers — the phase-close digest and, as of V6-4 (2026-07-07), episodic-to-semantic consolidation, which reuses the same `kind: crystallized` + five-field digest shape for its promoted entries rather than adding a separate `semantic/` folder. `procedural/` (distilled how-to, the next tier up) stays designed-for — see *How it grows*.

**Archive at every tier.** Each tier carries a cold archive for retired content — `_vault-archive/` at the `Agent/` root, `memory/_archive/` inside the memory tree, and a `_archive/` beside the projects in `desk/`. Recall **skips them by default**, so the record stays cheap to load as it grows; it opens only on deep research, an explicit ask, or granted permission. Nothing is hard-deleted — "prune" means *move to `_archive/`* (markdown stays the source of truth; the revert-log is the undo). The per-tier archive policy follows the autonomy gradient: **T1** archives only on an operator-confirmed proposal; **T2** archives a curated artifact when its successor supersedes it; **T3** the agent archives its own cold entries on its own. *Capture* describes the decay pipeline that feeds the archive.

### Arcs — temporal grouping as metadata, not folders

Work inside a project comes in **arcs** — a V5/V6/V7/V8 wave, the architecture-governance track, consolidation-review, a lettered build wave (wave-b, wave-c, …). An arc groups everything one stretch of work touched: designs, decisions, plans, close-out artifacts. It needed a way to show up in the vault, and the deciding question was whether that grouping should be a folder or a frontmatter fact.

**In the permanent record, arc identity is a frontmatter field, never a folder.** A `decisions/` entry or a design outside `_harness/` gains an `arc:` value; it does not move. Three reasons a folder-per-arc would have been worse: arcs **complete** — a folder tree would accumulate dead branches for every closed arc forever, where a tag just stops being queried; a **move invalidates the vec-index and embedding paths** already computed against a note's current location, which a metadata stamp never touches; and an arc can be **cross-repo** (architecture-governance spans both agentm and crickets) — a folder can only live inside one project, but a tag can be stamped in both.

**`arc:` is its own frontmatter field, not a third segment folded into `group:`.** `group:` mirrors the entry's folder path exactly, and every tool that reads it (`save.py`, `vault_lint.py`) depends on that invariant holding. Arc is an orthogonal fact about *when* an entry was made, carried the same way `tags:` carries other cross-cutting facts.

**A new `kind: arc-index`** gives each arc one note, at `projects/<project>/arcs/<arc-slug>.md`, linking the designs, decisions, plans, and close-out artifacts that carry its `arc:` stamp. A cross-repo arc has one canonical arc-index, in the project that owns it, and a thin pointer note in the sibling project pointing over. The MOC generator (`moc_generator.py`) emits the link-list body straight from `arc:` stamps found in its walk, the same way it already groups by `kind:` today; a hand-written header above that generated list is fine.

**Arc values are a closed, checked set.** `arc_registry.py` (mirroring `kind_registry.py`'s shape) holds the known arc slugs; `vault_lint.py` flags an `arc:` value outside that registry the same way it already flags an unrecognized `kind:`. A new arc starts by joining the registry, not by an entry inventing a slug no index will ever collect.

**Folder moves stay confined to `_harness/` — gitignored working state, never the permanent record.** Two moves are sanctioned there, both reversible and both scoped to an arc that has actually closed: (a) the flat `PLAN.archive.YYYYMMDD-<slug>.md` files that pile up under a project's `_harness/archive/` group into an `archive/<arc>/` subfolder once that arc's plans are all done; (b) a closed arc's design folder moves from `_harness/designs/<arc>/` to `_harness/archive/designs/<arc>/` — crickets' `archive/designs/efficiency-automation/` already does exactly this, ahead of the convention being named. An arc still being worked (architecture-governance's Phase 3, v8-proving) stays put in `_harness/designs/` until it closes; nothing about this convention moves a folder before its arc is actually done.

### What a memory is — the entry contract

A memory is **one atomic entry**: a markdown note with a locked frontmatter block, stored under its kind's group. The frontmatter is what makes it addressable and curatable:

- **`kind`** — the classification above (routes storage, scopes recall).
- **`status`** — `active` / `superseded` — recall filters superseded entries out.
- **`always_load`** — the boot-injection gate: an entry with `always_load: true` is assembled into context at session start (**as-built, the gate is `_always-load/` directory membership** — the authoritative source; the field mirrors it); the **heat policy flips this field** as the entry heats up or cools (the [Experience design](agentm-experience-and-dreaming.md)).
- **`supersedes`** — a back-link to the entry this one replaces (the supersession chain — see Capture).
- plus `created` / `updated` / `tags` / `slug`.

The content rule is **engagement, not encyclopedia**: an entry captures *why it mattered here and how to apply it*, not a generic description. **One note is one fragment** — small, indexable on its own — and **densely linked to its neighbors**. Beyond the typed `supersedes:` back-link, a note cross-references related entries with Obsidian `[[wikilinks]]`, the native interconnection substrate; the engine keeps those links sound (link-integrity discovery across the corpus, `notes_link_discovery.py`). Linking is **first-class**: a well-connected fragment is what lets the vector index, and later the V6 knowledge-graph, retrieve over *relationships*, not just text.

### How storage is served — one port, every caller through it

Everything agentm remembers reaches disk through a single **storage port** — the seam. The discipline is strict: *there is exactly one way to storage, and every caller goes through it.* Read bottom-to-top — three layers, each with one job:

1. **The storage seam — the one port.** The only layer that talks to a concrete store. `device-local` and `obsidian-vault` are interchangeable adapters; **more can be added** by implementing the same contract. Nothing above knows whether bytes land on the local filesystem or a synced vault — that ignorance is the point of a port.
2. **The memory engine — the one set of verbs.** `save` · `recall` · `forget` + the cross-cutting logic, every verb reaching the store *through* the seam.
3. **Inbound adapters — the ways in.** **In-process** (always present, a plain library call, zero daemon — the simple local case) and the **MCP server** (opt-in, a thin transport shim forwarding to the *same* engine).

![How storage is served, three layers: inbound adapters (in-process always-present, MCP server opt-in) reach the memory engine; the engine reaches the storage seam (selector + StorageBackend contract); the seam dispatches to interchangeable backends (device-local, obsidian-vault). Thick = always-present path, dotted = opt-in](diagrams/agentm-memory-storage-serving.svg)

The MCP server **belongs above the seam, as a client of it** — never underneath (that would force a daemon onto the simple local case and invert the layering; V5-0 put the mutex + content-hash CAS into the storage *primitives* precisely so the system needs no daemon). The seam, selector, device-local backend, and MCP shim are genericizable → **agentm substrate**; the `obsidian-vault` backend implements the contract one-way up → a **crickets backing plugin**.

The **MCP server** carries five key design choices:
- **Singleton streamable-HTTP** — one daemon, many sessions (`Mcp-Session-Id`), collapsing the host fan-out to a single writer alongside the CLI. Not stdio: stdio spawns one server per client, giving N OS processes on `vault_mutex` — safe but not single-writer.
- **Four snake_case tools**: `memory_search` · `memory_append` · `memory_capture` · `memory_forget`. Not dot-names: OpenAI-family MCP hosts reject them. (A fifth, `memory_recall`, was retired — R0.9; `memory_capture` was added by the capture design's front-door plan, FRIDAY ladder feature 2 — see the amendment log for both.)
- **Soft-delete**: `memory_forget` flips `status → deleted` + stamps `deleted_at`; the file is never unlinked. Not hard-delete: GDrive sync resurrects a hard-deleted file from propagation cache.
- **Loopback-first** (`127.0.0.1` / Unix socket): the remote tier (cross-device via OAuth 2.1 tunnel) is a deferred v1.1 addition.
- **Built on FastMCP, pinned `>=3,<4`** — with the official MCP SDK as a named fallback. Not unpinned: a FastMCP major can move the transport surface under the server.

**As-built vs. target.** Today harness *state* routes through the seam, but memory **entries** and the MCP server still write the vault directly — reaching around the port. Routing `save`/`recall`/`forget` through the engine→seam and re-platforming the MCP tools is **V5-14** (see References).

### Capture — the write protocol

The goal is concurrency-safe writes: when two sessions save to the same synced backend at once, both land and neither corrupts the other. A memory reaches disk through the V5-0 write protocol — a single `atomic_write` (temp → `fsync` → rename), guarded by an advisory **per-backend mutex** (a `mkdir` lock with an mtime heartbeat + stale-takeover, living *outside* the synced store) and, for replace-style files, a **content-hash compare-and-swap** that re-reads inside the lock before committing. Coordination lives in these *primitives*, not a daemon. *(Honest boundary: this is grounded at the seam — the `backend.write` body that composes these for the vault lives in the `obsidian-vault` plugin.)*

**Supersession is archive-then-replace.** A new entry that evolves an old one flips the old to `status: superseded` and sets a `supersedes:` back-link from the new, so the history is an **auditable link-chain**.

**Archive, decay, and prune.** Supersession is one road into the archive; the other is **decay** — an entry that goes cold over time is retired to its tier's `_archive/` rather than left to bloat recall. Three arms run today: heat curation demotes a cold always-load entry to its group root, `/memory evolve` archives a superseded entry, and **per-note lifecycle tiering (V6-1) shipped 2026-07-07** — an optional `lifecycle_tier: durable|volatile` frontmatter field, defaulting to volatile, that `harness/skills/memory/scripts/lifecycle.py` reads alongside two hardcoded decay-exempt categories (`kind: failure-incident` entries and any entry under a `decisions/` path segment, both always durable regardless of the tag). A volatile note decays exponentially (30-day half-life) from its last genuine recall access, tracked in a `.lifecycle.json` vault-root sidecar mirroring the existing `.heat.json` heat-policy pattern; only `recall.py`'s `prompt_submit()` resets that clock, so a lint pass, an index rebuild, or a future dreaming pass touching the file never resets it by construction. `recall.py`'s `query()` now returns `lifecycle_tier` + `decay_score` on every result, and the formatted recall-hit text surfaces the tier. **Episodic-to-semantic consolidation (V6-4) shipped 2026-07-07** — `harness/skills/memory/scripts/consolidate.py` promotes a recurring target (referenced by at least 3 distinct episodic entries, using V6-2's typed-edge extractor as the recurrence signal) to a single durable, decay-exempt `kind: crystallized` entry, carrying a `derived_from` provenance field naming its sources; the episodic sources are never deleted or modified — only the new entry is added above them. Every consolidation write routes through the revert-log (`RevertLog.record_and_apply`), satisfying the provenance-edge prerequisite named below. **A whole-corpus dreaming pass that moves cold notes to the archive shipped 2026-07-18** — see [AgentM Auto-Organization](agentm-auto-organization.md), this section's own designed-for tail built out. A new tidying stage in `dream.py` retires a non-exempt entry past five years without a genuine recall to its tier's `_archive/`, with a one-cycle digest preview at 4.5 years; the stepped rank-curve retune that feeds it ships shadow-first, gated on the pinned retrieval eval never regressing before it drives live ranking. The earlier "staging gate" framing below — an autonomous job proposes to a staging inbox, the operator confirms before anything goes cold — is **superseded**: the auto-organization design's own review rounds concluded nothing is ever deleted, only moved, and a revert log makes every move undoable, so every tidying move auto-applies with no confirmation step, the same "retire it, reversible via the undo/revert log" basis compression's own 2026-07-11 auto-apply ruling already established. Semantic → procedural promotion and the phase-close crystallization digest's own separate trigger stay **designed-for**, framed in V6/V7. Prune resolves to archive; there is no hard delete.

**Writing T1 (personal) takes a separate, explicit call.** The normal write path reaches T2/T3 inside `Agent/`. Personal content sits outside `vault_path`, so writing it goes through a distinct seam call that the operator's request authorizes — the line between agent-controlled and user-controlled space (the [memory-storage-seam design](memory-storage-seam.md)).

### Surface — the recall loop

Memory is injected by two hooks. At **session start**, the **always-load set** (entries gated by `always_load: true`) is assembled under a hard ~500 ms budget. On **every prompt**, a five-step engine runs under ~300 ms:

1. **tokenize** the prompt;
2. **embed** it (a local embedder, degrading to a deterministic stub — the API embedder mode was removed) and search the local sqlite-vec index for the top-K by cosine similarity;
3. **keyword-grep** (filtering `status: superseded`);
4. **merge** (semantic-weighted: ~0.85 similarity + ~0.05 keyword);
5. **dedup** against always-load, and return the top few.

**A stream runs whole or not at all.** The 300 ms figure is a promise about interactive latency, and it is kept by **admission**, not by truncation: each half of the search is started only if it can finish, and a half that gets cut short has its results discarded. Cheap checks precede expensive ones — the vector index is opened before the query is embedded, because opening costs about a millisecond and embedding costs about four seconds from cold, and a host that cannot open the index would otherwise pay the whole load to produce a vector with nowhere to go. A cold embedder is declined outright under an interactive budget and attempted only where the budget can absorb it, such as the 10 s `query` CLI.

Truncation was the original contract and it was wrong, because a partial search here is not a partial *result*. The lexical scorer derives IDF and average document length from the candidate set its walk actually reached, so stopping halfway produces a different ranking over an arbitrary subset rather than the first half of the real one — confident-looking entries that no complete search would have chosen, indistinguishable downstream from real ones. Silence is the honest degradation. For the same reason a zero-result recall must say **which** streams were blocked and why: `Loaded 0` reported identically for "searched, found nothing" and "could not search" is what let this fail silently for months (see the amendment log).

Recall is **token-budgeted** and **scoped by kind + phase** — a phase pulls the kinds its budget allows, not a flat top-K over the whole corpus *(as-built today: a flat token-budgeted top-K; the `--kind`/`--phase` scoping is designed — see Risks)*. The vector index is **device-local and never synced** (the local-index tier), with mtime-vs-indexed-at drift detection that falls back to grep when an entry changed since it was embedded. Recall **skips every tier's `_archive/` by default** — the cold store stays out of the always-load floor and the per-prompt search, so a growing record does not inflate what each call pays. An `--include-archive` opt-in (mirroring `--include-inbox`) widens the walk over the archive for deep research, an explicit ask, or a granted request; the vector index still covers archived entries, so an opened search ranks them on the same budget.

### How it grows — into an interconnected knowledge base

The record is built to **compound**. Three things turn a growing pile of entries into a navigable knowledge base:

- **Learning populates it.** Reflection mines durable entries from finished sessions, and forward learning + deep research reach approved sources and the web for any task and bring back what's worth keeping — typed and filed like anything else (the [Experience design](agentm-experience-and-dreaming.md)). The more agentm works and reaches outward, the larger and richer the record. This is the growth engine.
- **It's interconnected by wikilinks — built.** Every entry cross-references its neighbors with `[[wikilinks]]`, and the engine maintains link integrity. The links are the connective tissue: the substrate everything else builds on.
- **It becomes navigable by an index over the markdown — built.** A device-local vector index makes the corpus semantically searchable, and the **SQLite metadata table + hybrid `--filter` recall (V6-11) shipped 2026-07-06** — a query can now narrow by `kind`/`project`/`status`/`tag` in the same SQL-joined-with-vector query. **The knowledge-graph extraction layer (V6-2) shipped 2026-07-07** — `harness/skills/memory/scripts/graph.py` walks a note's raw markdown, finds every `[[wikilink]]`, drops occurrences inside a fenced code block or inline backtick span, and classifies each surviving occurrence into one of nine typed edges (`uses` / `depends-on` / `contradicts` / `caused` / `fixed` / `supersedes` / `decided-in` / `implements` / `references`) by matching cue phrases in the surrounding prose, plus a second pass over frontmatter `supersedes:`/`superseded_by:` fields. It is deterministic — zero LLM calls, proven by a red test that AST-walks the module's own imports. **The ranking itself now runs Reciprocal Rank Fusion — shipped 2026-07-07 (V6-3).** `recall.py` fuses ranked lists (score = sum of `1/(60+rank)` across sources) instead of the old weighted sum (`sim * 0.85 + keyword * 0.05`); the lexical stream is now real BM25 (term-frequency saturation + IDF + a deterministic stemmer) rather than a raw substring count, a MemoryOS-style 4-level fallback cascade degrades gracefully (hybrid → vector-only → lexical-only → unranked metadata-filter-only) as signals become unavailable, and a small abstraction-altitude rank boost prefers `_index`/`_summary` anchor files at near-ties. **Chunking (V6-10) and time-weighted retrieval (V6-12) shipped 2026-07-07** — the BM25 lexical scorer now scores each candidate by its single best-matching paragraph-aware chunk (`harness/skills/memory/scripts/chunking.py`) instead of one fixed 500-character window from the start of the file, and the per-note `decay_score` now multiplies every candidate's fused ranking score before sorting, so a stale volatile-tier note genuinely ranks below an equally-relevant fresher one. **Consolidation (V6-4) shipped 2026-07-07** — `harness/skills/memory/scripts/consolidate.py` promotes episodic entries to a durable semantic entry once the same reference target recurs across at least 3 distinct episodic entries (reusing V6-2's typed-edge extractor as the recurrence signal, not a second mechanism); the consolidated entry carries a `derived_from` provenance field and reuses crystallization's five-field digest schema, and the episodic sources are never deleted or modified — only added above (the never-delete invariant). **Still designed-for:** folding the knowledge graph in as one more RRF stream, multi-hop traversal over its edges, and synonym expansion (an honest, undone v0 gap).

That is the trajectory toward a true knowledge base: a typed, densely-linked, indexed record that accumulates and compounds as agentm learns — the brain the other three pillars stand on. The typed entries, the wikilink substrate, the vector index, the knowledge-graph extraction, RRF-fused hybrid ranking, chunked passage scoring, time-weighted decay, and episodic-to-semantic consolidation are built today; graph fusion into retrieval, multi-hop traversal, and synonym expansion are **designed-for, framed in V6** (Risks).

## Dependencies

- **The seam design** — [memory-storage-seam](memory-storage-seam.md) holds the deep storage contract (A2-fold, launched 2026-06-24); this pillar points down to it.
- **Experience grows the sole-owned space** — reflection, heat curation, dreaming write here ([Experience design](agentm-experience-and-dreaming.md)); the heat policy owns the `always_load` gate.
- **Opinions keep their learned half here** — an opinion's vault supplement is a memory entry ([Opinions design](agentm-opinions-and-gates.md)).
- **Personas draw their state here** — Memory is the pseudo-persona beneath all ([Personas design](agentm-personas.md)).
- **crickets backs the store** — `obsidian-vault` implements the `StorageBackend` contract, one-way up.

The never-delete invariant holds: consolidation only adds the new entry above its sources, never deletes or edits them. Every consolidation write routes through the revert-log primitive (`RevertLog.record_and_apply`, from the sibling dreaming plan merged earlier this session) rather than a direct file write; `scripts/test_consolidate.py`'s own red test reverts a consolidation run and confirms the written file disappears, proving the write was genuinely journaled. `scripts/health/eval_v6_consolidate.py` measured against a synthetic fixture (not the real vault — running consolidation against real content stays a deliberate, operator-invoked action, matching the dreaming pipeline's stage-and-confirm posture): entries needed for full topic coverage dropped 3 → 1, with zero recall regression (the consolidated entry is found, and all 3 sources remain independently findable). Honest caveat: because sources are never deleted, raw vault file count increases with each consolidation rather than decreasing — the "reduces corpus size" framing is satisfied as reduced retrieval redundancy, not reduced file count. This closes the "How it grows" + Risks sections' last named designed-for item from the 2026-06-21 amendment's trajectory; what remains designed-for after this task is graph fusion into retrieval ranking, multi-hop traversal, and synonym expansion. *Re-audit trigger:* revisit `MIN_RECURRENCE` (3, a named v0 default) once real query volume against the live vault exists; reconcile here when semantic → procedural promotion or the whole-corpus dreaming pass start consuming `derived_from` chains.

**2026-07-07 — V6-10 chunking + V6-12 time-weighted retrieval shipped (PLAN-wave-e-v6-index task 6).** New `harness/skills/memory/scripts/chunking.py` adds a deterministic, paragraph-aware `chunk_text()`, wired into `recall.py`'s BM25 lexical scorer as max-passage scoring: each candidate's score is now its single best-matching chunk's score, not one fixed 500-character window from the start of the file — directly fixing a real gap task 5's own eval had traced, where long documents whose relevant content lived past the first 500 characters scored zero regardless of the ranking formula. Chunks are computed on-the-fly at query time, not persisted as new `entry_meta` columns; a chunk-level vector-embedding pipeline is a separate, larger future build. Separately, `decay_score` (task 3's `lifecycle.py`) now multiplies every candidate's fused ranking score before sorting, not just a label attached to already-decided results, so a stale volatile-tier note genuinely ranks below an equally-relevant fresher one. This task's own eval caught two real bugs before shipping: the chunking implementation's BM25 avgdl (length-normalization baseline) was accidentally computed over the whole vault instead of just the candidate set, silently making long documents score worse; and the decay anchor fell back to a note's `created` date instead of `updated` when no access history existed, wrongly penalizing a same-day-edited reference document for staleness it didn't have, purely because the retrieval system had never queried it before (a cold-start bug). Both were found and fixed within this task. Measured against the real vault (cumulative effect of this task plus task 5's RRF change together, vs. the original pre-task-5 baseline): recall@5 improved 31.1% → 73.5%, precision@5 improved 7.3% → 17.3%, queries finding at least one correct answer went 8 → 18 of 22, and 10 of 29 gold answer-pairs are now found only by the new retrieval stack. The compression proxy softened very slightly (1.875 → 1.83) — outweighed by the large accuracy and discovery gains, clearing this project's own guard rule against merging a ranking change on accuracy improvement alone. *Re-audit trigger:* revisit the chunking window size and the decay-anchor fallback once real query volume against the live vault exists; reconcile here when consolidation tiers or a chunk-level embedding pipeline start consuming chunk boundaries.

**2026-07-07 — V6-3 RRF hybrid retrieval shipped, replacing the weighted-sum merge (PLAN-wave-e-v6-index task 5).** `recall.py`'s ranking formula changed from a weighted sum (`combined = sim * 0.85 + keyword * 0.05`) to Reciprocal Rank Fusion (RRF): score = sum of `1/(60+rank)` across each source's ranked list. The lexical signal upgraded from a naive substring-count to real BM25 (term-frequency saturation + inverse-document-frequency + a deterministic stemmer). Added the MemoryOS 4-level fallback cascade — hybrid retrieval → vector-only → lexical-only → unranked metadata-filter-only — so ranking degrades gracefully as signals become unavailable, and an abstraction-altitude rank boost that prefers `_index`/`_summary` anchor files at near-ties. Knowledge-graph fusion (task 4's edges) was explicitly kept out of this task's scope — folding the graph in as one more RRF stream and multi-hop traversal are separate future items; synonym expansion is an honest, undone v0 gap. Paired with `scripts/test_recall_rrf.py` (12 new tests: RRF arithmetic and deterministic tie-breaking, BM25 stemming + IDF-favors-rare-terms, the altitude boost, and each reachable fallback-cascade tier) and `scripts/health/eval_v6_retrieval.py` (the real-vault half of the eval, comparing old vs. new formula on task 2's 22 gold queries, gracefully skipping in CI, wired into `run-fast-tier.sh`). Measured against the real vault: recall@5 improved 31.1% → 46.2%, precision@5 improved 7.3% → 10.9%, a compression proxy (average rank position needed to find the first correct answer — lower means fewer results need injecting for the same coverage) improved 1.875 → 1.36, and a discovery-rate of 17.2% (5 gold answers found only by the new formula, that the old one missed entirely) — all three signals improved together, clearing this project's own guard rule against merging a ranking change that only improves raw accuracy without also improving compression or discovery. One honest environmental caveat: this sandbox can't load the sqlite-vec extension, so vector similarity was unavailable for both the old and new formula in this run — the comparison measured is BM25+altitude vs. the old raw-keyword-count, not the full vector+lexical fusion; that caveat is noted in the eval script itself, not hidden. Worth recording as a real example of why this project builds the eval before declaring a ranking change done: the first draft of the abstraction-altitude boost was miscalibrated (roughly 60x too large relative to genuine RRF score gaps between adjacent ranks) and actively broke retrieval quality — recall crashed from 31% to 1.5% — before the eval caught it and it was fixed down to a tie-breaking-only magnitude. *Re-audit trigger:* revisit once knowledge-graph fusion (folding task 4's edges in as an RRF stream) or synonym expansion land, since both would change the source mix this formula fuses over.

**2026-07-07 — V6-2 deterministic typed-edge knowledge graph shipped (PLAN-wave-e-v6-index task 4).** New `harness/skills/memory/scripts/graph.py` adds a zero-LLM, regex/heuristic extraction cascade that reads a note's raw markdown and produces typed edges: it finds every `[[wikilink]]`, excludes occurrences inside a fenced code block or inline backtick span (so a code-example placeholder that merely looks like a link is never extracted), classifies each surviving occurrence into one of nine edge types (`uses` / `depends-on` / `contradicts` / `caused` / `fixed` / `supersedes` / `decided-in` / `implements` / `references`) by matching cue phrases in the surrounding prose, and runs a second pass over frontmatter `supersedes:`/`superseded_by:` fields independent of wikilink wrapping. This is one RRF retrieval stream to be fused in a later task, not the retrieval spine itself — markdown stays source of truth, and multi-hop graph traversal is explicitly out of scope here (a separate future verb). Paired with `scripts/test_graph_extract.py` (19 fully-synthetic unit tests, CI-safe, including a red test that AST-walks `graph.py`'s own imports to prove zero LLM/network calls anywhere in the extraction path) and `scripts/health/eval_v6_graph.py` (the real-vault half of the eval, reading the operator's private Obsidian vault via `MEMORY_VAULT_PATH`, gracefully skipping in CI, wired into `scripts/health/run-fast-tier.sh`'s health-dashboard JSONL emission under the "memory persist+recall" axis). Measured against the real vault: recall 1.0 (145/145 labeled true edges found), trap-rejection 1.0 (12/12 deliberate non-edge traps correctly never extracted), type-classification precision 0.766 (111/145 edges got the exactly correct type of the 9). This is an inaugural measurement — no precision/recall floor existed before this task, since the graph didn't exist yet — and a future plan deciding whether to fuse multi-hop traversal into retrieval ranking will use this number as its reference floor. This is the extraction slice the 2026-06-21 amendment below named as the trigger for flipping the knowledge-graph from designed-for to as-built; RRF fusion (V6-3/10), consolidation tiers, chunking, and multi-hop traversal stay designed-for. *Re-audit trigger:* the 0.766 type-classification precision is untuned against a larger labeled set — revisit once the graph feeds live retrieval ranking; reconcile here when RRF fusion (V6-3) starts consuming these edges.

**2026-07-07 — V6-1 per-note lifecycle tiering shipped (PLAN-wave-e-v6-index task 3).** New `harness/skills/memory/scripts/lifecycle.py` adds an optional `lifecycle_tier: durable|volatile` frontmatter field (via `save.py`'s locked `FRONTMATTER_FIELD_ORDER`, defaulting to volatile when omitted) plus two hardcoded decay-exempt categories regardless of that tag: `kind: failure-incident` entries and any entry under a `decisions/` path segment.
