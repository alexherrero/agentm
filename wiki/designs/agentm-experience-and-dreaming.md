# AgentM Experience & Dreaming

## Objective

Experience is **how agentm gets better over time** — it turns the agent's own past sessions, and the wider world, into sharper judgment, so the next session starts further ahead than the last. It is what makes the memory *grow* rather than just persist.

## Overview

Experience runs in **two directions**:

- **Backward** — learning from its own past. Every finished session leaves something behind that sharpens the next. **Built today.**
- **Forward** — learning from the world. On a schedule, when configured, the agent reaches approved sources, brings back ideas to improve itself, and surfaces them to you. **Thin v1 built, opt-in.**

## Design

### Backward experience

- **Reflection** *(built)*. After a session ends, a pass mines the transcript for durable entries, each **classified by `kind`** (preference · workflow · fix · …; see the [Memory System](agentm-memory-system.md) for the taxonomy). It routes each candidate by confidence into **three lanes**: **HIGH** → auto-saved; **MEDIUM** → the inbox or surfaced for review; **LOW** → the inbox to triage later. The routing *mode* is set by `MEMORY_REVIEW_MODE` (auto / silent / interactive); the confidence tiers themselves are hardcoded, not a tunable threshold. A Stop-event hook runs it at session end; an idle hook catches sessions that crashed before it could fire. Reflection also seeds **idea incubation** (a skeleton an idea-researcher sub-agent later fills).
- **Inbox triage** *(built 2026-07-11; auto-apply retired the confirm-gate the same day, second pass)*. Reflection's MEDIUM/LOW-confidence lane routes to `personal/_inbox/` and stops there — nothing moved an entry out of `status: inbox` again until this landed; the backlog had grown to 1,565 notes (55% of the whole vault) with only 2 ever transitioning. `/memory inbox --bulk-review` (`harness/skills/memory/scripts/inbox_triage.py`) scans the still-untriaged pool and proposes one of three dispositions per entry: **promote** (reinforced by repeated occurrence, or a real content match across 3+ entries, graduates to the same canonical destination reflection's own HIGH-confidence path already writes to), **merge** (a near-duplicate pair, reusing dreaming's own `difflib` similarity stage against the inbox pool rather than a second implementation), or **expire** (stale and unreinforced past a TTL, archived in place — never deleted). Every proposal stages through the same `_dream-staging/` → `dream_confirm.py` confirm/revert-log path dreaming already built, unmodified. It shipped confirm-gated for its first-ever run: a first-run **cutover marker** (`_meta/inbox-triage-cutover.json`) separated the pre-existing backlog from anything captured afterward, and every disposition against the backlog stayed confirm-gated no matter what. The operator personally reviewed and confirmed that entire first-run backlog — 635 proposals across 1,565 entries, zero errors — and on the strength of that supervised pass directed that confirm-gating retire going forward: **every disposition now auto-applies by default**, promote/merge/expire alike, regardless of the source entry's era. The cutover marker still exists and still labels an expire proposal's era in the digest, but purely as information now, not a gate. As of 2026-07-18 (auto-organization part 3 task 4), the CLI is no longer the only door into this engine: `dream.run_dream_and_auto_apply()` — the wrapper `dream.py`'s CLI and the weekly `dream.yaml` job actually invoke — now also runs it automatically, as a sibling sub-run inside every weekly dreaming cycle. `/memory inbox --bulk-review` is unchanged and stays the on-demand door into the identical engine for anyone who wants to run it outside that cadence. See the amendment log for the full rationale of all three landings.
- **Heat-based curation** *(built)*. Which memories load *every* session changes with use: a heat policy promotes an on-demand entry into the always-load set once it's been hit enough times across enough distinct sessions, and demotes cold ones — down to a safety floor, leaving pinned entries alone. Built and tested; it keeps the always-load set earning its token cost.
- **Crystallization** *(designed and built, phase-close trigger + digest primitives; distillation deferred behind a named seam)*. Distils an exploration into a structured digest — question · investigation · findings · lessons · open threads — instead of leaving raw transcript fragments behind. It's the phase-close counterpart to dreaming's whole-corpus pass. **`harness/skills/memory/scripts/crystallize.py`** (digest schema + write/read primitives built 2026-07-07, `PLAN-wave-e-experience` task 2; phase-close trigger designed + built 2026-07-26) ships the five-field digest schema — `crystallize_exploration()` writes a `kind: crystallized` entry through the existing `save_entry()` (no new store), `parse_digest()` reads one back and raises on a missing section — plus the trigger itself: `stage_candidate()` / `list_candidates()` / `drop_candidate()` / `count_pending_candidates()` manage bare markers under `<vault>/_crystallize-staging/`, staged by `orchestration_phase.stage_crystallization_candidate()` as a sibling step on both `post-work` and `post-release` (see the *Crystallization's phase-close trigger* section below for the full nine-call design). Composing a digest from a staged candidate stays manual — `exploration_judge_available()` names the deferred judgment/distillation seam, always `False`, since the chain that stages cannot dispatch a model to judge or distil. **`[PENDING-IMPL]`** narrows to just that seam.

### Forward experience — designed and built (thin v1, opt-in)

Backward learning can only sharpen what the agent has already seen; forward learning brings in what it *hasn't* — a periodic, opt-in pass that reaches approved sources and surfaces what's worth knowing.

- **Approved-source learning.** On a schedule (operator-configured), the agent pulls from a list of **approved sources** — feeds, named repositories, the web — and mines them for ideas that could improve it: techniques, tools, patterns, conventions. What it finds is **surfaced to you** to accept or pass on; nothing is adopted silently. The source list and the cadence are operator-controlled — opt-in by design.
- **The approved-source pipeline exists now:** `harness/skills/memory/scripts/forward_learning.py` (built 2026-07-07, `PLAN-wave-e-experience` task 1) generalizes the import watchlist's shape — find → screen → surface — beyond skills to ideas, patterns, and references. Sources are read from `_meta/forward-learning-sources.json`, which is **absent by default**: no config means a scan finds nothing, so the pipeline is inert until an operator opts in by naming sources. Unlike the import watchlist below, this v1 is a **single deterministic pass** — one rubric (score thresholds reused from `adapt_skills.py`: ≥3 HIGH, ≥1 MEDIUM, else LOW) does find, screen, and classify together, with no `adapt-evaluator`-style semantic judge sub-agent. A Pass-2 LLM judge is a natural v2 graduation, not built here. MEDIUM/HIGH candidates land in a new, generalized `personal/_watchlist/` (sibling to the skill-specific `personal/_skill-watchlist/`); LOW is dropped, never written. Per-source watermarks live in `_meta/forward-learning-cache/`. Nothing outside those two locations is ever touched — no auto-adoption anywhere else.
- **The import watchlist (adapt-don't-import)** was the one piece that existed before this task, and still owns *skills* specifically: a deterministic rubric (`adapt_skills.py`) enriches candidate external skills, a judge sub-agent (`adapt-evaluator`) classifies them HIGH/MEDIUM/LOW, and a review CLI (`watchlist_review.py`) lets you promote / dismiss / defer. `watchlist_review.py` is now generalized (same task) so the same CLI reviews both `_skill-watchlist/` and the new `_watchlist/` as one merged surface — including a fix so `dismiss_entry` archives each entry back into whichever root it actually came from, rather than always the skill-watchlist archive.
- **The runner (the background-job executor) — built 2026-07-06.** Backward learning rides session events; forward learning has no session to ride, so it runs on the **runner** — fired by the host's scheduler (see the [Runner design](agentm-runner.md)). `templates/jobs/forward-learning.yaml` (built 2026-07-07) registers the pipeline as a `schedule: daily`, `dry_run: true` job manifest, opt-in like [dreaming's job template](agentm-runner.md) — no `budget:`, since the thin v1 pass makes zero LLM calls. The runner is also the home for other periodic upkeep (dreaming, index maintenance); it's a shared substrate primitive the Maintainer and Researcher persona loops wait on too.

**Designed and built, thin v1, opt-in.** The approved-source pipeline is real and tested (20 tests across `test_forward_learning.py`, `test_watchlist_review.py`, `test_forward_learning_job.py`), but it isn't the full design: no sources are configured by default, screening is one deterministic rubric rather than the two-pass deterministic-rubric-then-semantic-judge split the import watchlist itself uses, and the job manifest ships `dry_run: true` requiring manual `.harness/jobs/` install like every other runner job template. *Re-audit trigger:* revisit this note if a Pass-2 semantic judge is built, or once real approved sources are configured and calibration evidence justifies flipping `dry_run` to `false`.

### Dreaming — designed and built (dry-run / opt-in)

Memory's "sleep": a whole-corpus consolidation pass — dedup, contradiction triage, compression, insight-generation — producing a derived insights layer. The design is locked. Its prerequisite, the revert-log primitive, exists (`harness/skills/memory/scripts/revert_log.py`, built 2026-07-07), and the pipeline itself now has a thin, operator-invoked implementation: `harness/skills/memory/scripts/dream.py` (`run_dream(vault_path, *, run_id=None) -> DreamDigest`, built 2026-07-07). It runs dedup (stdlib `difflib`, threshold 0.92), contradiction triage (same-`slug`-differing-body, advisory only), and compression (`supersedes:`-chain compaction, never deleting a source) as **proposal-only** stages — no source file is mutated by a run — and writes every disposition to a staged digest (`_dream-staging/<run_id>/digest.md`) plus a machine-readable manifest (`_dream-staging/<run_id>/proposals.json`) carrying a prospective revert pointer for the confirm step to apply. Insight-generation is the one stage that writes directly, always as an additive `status: candidate` file under `_dream/insights/<run_id>.md`, per the design's own carve-out for non-source-touching writes.

The confirm step now exists too: `harness/skills/memory/scripts/dream_confirm.py` (`list_pending`, `confirm`, `expire_stale`, built 2026-07-07) is the human path a staged **dedup** or **contradiction-triage** proposal applies through — `confirm()` calls `revert_log.RevertLog.record_and_apply(...)` directly against the manifest's structured mutations, never a source-file write of its own. An unconfirmed proposal carries a TTL (default 30 days, a calibration-era judgment call, not a locked design number); past TTL, `confirm()` raises rather than silently applying, and a separate `expire_stale()` bulk pass marks stale proposals expired without touching source files. Confirmation state lives in a sidecar (`_dream-staging/<run_id>/state.json`) next to the staging directory, not in the revert-log journal itself.

**Compression applies automatically as of 2026-07-11** (see the amendment log below): `dream_confirm.auto_apply_batch` (built alongside this amendment) sweeps every pending **compression**-stage proposal through the exact same `confirm()`/`revert_log.record_and_apply` path a human call uses — same TTL check, same one-shot guard, same journal — but with no operator confirm required, capped at `dream_confirm.DEFAULT_AUTO_APPLY_BATCH_CAP` (25) proposals per cycle. `dream.py`'s CLI now calls this by default (`run_dream_and_auto_apply`, the new entry point `main()` uses unless `--no-auto-apply` is passed); `dream_confirm.confirm()` itself is completely unchanged and still the only path for dedup and contradiction-triage. With this, the **manual path is end-to-end complete and fully revertible for all three stages**: an operator running `/dream` by hand today gets compression retired automatically and dedup/contradiction-triage staged for an explicit `confirm()` call, exactly the split the design's Objective and the 2026-07-11 ruling both describe.

The scheduled half now exists too: `templates/jobs/dream.yaml` (built 2026-07-07, cadence + batch cap reviewed 2026-07-11) registers the whole-corpus pass as a job manifest on the [Runner](agentm-runner.md) — `command:` wires `dream.py`'s CLI with an explicit `--batch-cap 25`, `schedule: weekly` + `lookback: 14d` stand in for the design's "activity-gated" framing until the runner's `gate:` field graduates from parsed-but-unevaluated to real (`scripts/runner/cycle.py`, as-built), and `tier: T3` reflects that insight-candidate writes (and now compression's own auto-applied writes) are new agent-generated content rather than operator-curated T2. It carries no `budget:` — the thin v1 pipeline makes zero LLM calls. Two things keep this from being a plain "ship it and forget it" flip. First, it ships **`dry_run: true`**: per the plan's own Constraints, a due cycle reports `ran=False, dry_run=True` and proves the command never executes at all — including the new auto-apply step, which only ever runs once the job itself runs — and promoting to live-apply is a separate, explicit future decision, not a consequence of the manifest merely existing. Second, `.harness/` is entirely gitignored in this repo, so the manifest can't live at a tracked path there — it ships as a tracked template at `templates/jobs/dream.yaml`, following the same `templates/` → `.harness/` copy precedent as `.harness/hooks/*` and `.harness/verify.sh`, and a repo opts in by copying it to `.harness/jobs/dream.yaml` by hand; `install.sh` has no automatic seeding step for runner jobs yet (this is the first job manifest shipped at all, ahead of forward-learning's or health-check's). Tested by `scripts/test_dream_job.py` (3 passing tests): the manifest parses against `scripts/runner/manifest.py`'s schema; a due cycle against the shipped template never touches `_dream-staging/`; and a cycle with `dry_run` overridden to `False` for the test only (the shipped template itself stays `dry_run: true`) produces a digest structurally identical to task 2's direct `dream.run_dream()` call.

**Designed and built, shipped dry-run / opt-in; compression auto-applies once the pipeline runs.** All four tasks are built and tested — the pipeline, the revert-log safety net, the confirm/expire flow (now split into a confirm-required half for dedup/contradiction-triage and a confirm-free auto-apply half for compression), and the scheduled job manifest — so this is no longer a bare `[PENDING-IMPL]` gap. But it isn't a plain as-built either: the manifest is a template a repo must deliberately copy into `.harness/jobs/`, not something `install.sh` seeds on its own, and even once registered it stays `dry_run: true` — the whole job, auto-apply included, never runs at all — until an operator separately promotes it to live. Once it does run (a manual `/dream` invocation today, or a promoted job later), compression proposals retire automatically while dedup/contradiction-triage proposals still stage to `_dream-staging/` for operator review. Re-audit this note when `install.sh` gains a seeding step or a repo's calibration evidence is recorded as sufficient to flip `dry_run` to `false`.

**A fifth stage — tidying — joined the pipeline 2026-07-18** (auto-organization part 1, [AgentM Auto-Organization](agentm-auto-organization.md)). `_stage_tidying()` runs alongside dedup/contradiction-triage/compression inside `run_dream()`'s existing hand-wired sequence (there's still no stage-registry — this new stage joins the same way every other one did), and covers two lanes: a memory-kind entry past five years without a genuine recall access moves to its tier's `_archive/` (a one-cycle digest preview at 4.5 years first), and a non-memory artifact — any entry with no `kind:` frontmatter field at all — untouched for a year moves to its tier's `_shelf/`, returning automatically the cycle after it's touched again. Both lanes joined `AUTO_APPLY_STAGES` alongside compression (now `{"compression", "tidying"}`) on the same auto-apply basis: every move is reversible through the revert log, so none of it waits on operator confirmation. A new anomaly breaker (`dream_confirm.check_tidying_anomaly`) guards tidying's own auto-apply specifically: a cycle proposing several times a trailing 8-cycle baseline applies nothing from that stage — not a capped partial batch — and flags a digest section plus `_meta/dream-anomaly-latest.json`, while compression's own auto-apply continues unaffected. This is the first of auto-organization's three parts. The write-time linker (part 2 task 3) hooks into the save/drain path instead of extending this pipeline — see the paragraph below for why. The weekly link-improvement sweep (part 2 task 4, also below) and part 3's dedup-plus-lint do extend `run_dream()`'s own sequence further, not add a second one.

**A sixth stage — link_improvement — joined the pipeline** (auto-organization part 2 task 4; see [AgentM Auto-Organization](agentm-auto-organization.md) for the full design and its own "As built (task 4)" note). `_stage_link_improvement()` runs alongside dedup/contradiction-triage/compression/tidying inside the same hand-wired `run_dream()` sequence, finding notes changed since the last sweep — tracked by its own dedicated cursor (`_meta/link-sweep-cursor.json`), not `graph_snapshot`'s `touched_paths`: an earlier version reused that signal and a review caught it silently consuming the write-time linker's own touch, so the weekly sweep never saw the very notes most likely to have qualifying neighbors — and proposing both-directions links for clear candidates above `write_time_linker.CONFIDENT_SIMILARITY_THRESHOLD` (0.85), applied through a new shared `write_time_linker.merge_related_slugs()` helper. It joined `AUTO_APPLY_STAGES` too (now `{"compression", "tidying", "link_improvement"}`) on the same reversible-via-the-revert-log basis. Two departures from the design's literal wording: the cheap-model band reserved for the ambiguous middle-similarity band was never built — `dream.cheap_model_tier_available()` always returns `False`, an explicit tracked seam rather than a silent drop, so every ambiguous candidate degrades to "left unlinked," the same fallback the design already names for a spent budget or an unavailable tier — and unlike tidying, this stage has no dedicated anomaly breaker yet, only the fixed `_LINK_IMPROVEMENT_BATCH_CAP` (25) per-cycle cap, a known and deliberately deferred gap. The same stage picked up a second job with task 6: the 880-note backfill now runs through it too, attempting a separately-capped batch (`_LINK_BACKFILL_BATCH_CAP`, also 25) of the vault's orphan notes each cycle through the identical link flow and emitting `kind="backfill"` proposals — still `stage="link_improvement"`, so auto-apply and the revert log treat them the same as any other candidate — see [AgentM Auto-Organization](agentm-auto-organization.md) for the full as-built note, including the persisted attempted-set that rotates the backfill pool cycle over cycle. Task 7, the connectivity meter, landed alongside it — not a new stage, but a new pair of numbers computed inside `run_dream()`'s existing `corpus_stats`: `dream._connectivity_meter()` counts organic connectivity (notes with ≥1 real, non-generated link) and the linker's own `generated_link_count` independently, rendering both in the digest header every cycle. See [AgentM Auto-Organization](agentm-auto-organization.md#the-meters) for the full as-built note. That was the last task of `PLAN-auto-org-write-time-linking.md` — all 7 tasks (auto-organization part 2) are now shipped. *Re-audit trigger:* part 3 (dedup-plus-lint) extends this same pipeline further — reconcile here as it lands, and again if a cheap-model primitive or a link-specific anomaly breaker is ever built.

### Where the learning lands

What's learned routes into the **general memory** the same way anything else does — as **`kind`-classified entries**: a learned preference, workflow, fix, or domain-reference becomes a typed entry, classified by reflection on the way in (see the [Memory System](agentm-memory-system.md)). Two other destinations sit alongside it:

- **The idea incubator / watchlist** — an ingested idea, article, or candidate skill (forward learning) lands here **for later review**, not adopted silently.
- **The Opinion supplement** — the part that's a *standard* sharpens an opinion's learned layer over time (the *accumulate* loop — built end-to-end; see the section below and the condensed twin in the [Opinions design](agentm-opinions-and-gates.md)).

Everything routes through the existing memory engine — no new store; heat curation runs continuously over the always-load set.

### The Experience → Opinions accumulate loop — built

**Spec landed 2026-07-07 (`PLAN-wave-e-experience` task 3); Stage 1 built 2026-07-24 (v9.1.0); Stages 2-3 designed 2026-07-25 and built the same day ([PR #380](https://github.com/alexherrero/agentm/pull/380)).** This is the one pillar-to-pillar flow that had no contract: how a signal from Experience's capture paths becomes a lasting sharpening of an Opinion's learned supplement. What landed in 2026-07 was a design amendment rather than an implementable design — it named guards without naming the fields, stores, thresholds, and channels they run on. Stage 1 shipped the half that was buildable as written; the operator deferred the rest for a design pass rather than let a build guess at them, because this is self-modifying behavior and a wrong design accumulates wrong standards and then enforces them. The section below is the whole contract with those holes closed.

**The one-sentence design:** the accumulate loop is the style-learning loop generalized from voice to standards — the same edit-driven, operator-gated capture the wiki system already proved, with a recurrence gate in front and the coded base as an unoverridable floor behind.

**1 — Route, don't invent** *(built, v9.1.0)*. No new pipeline. The loop is a routing rule inside the capture paths that already exist: when reflection (session-close), edit-driven capture, or the watchlist produces a candidate that is *standard-shaped* — a rule about how work should be judged or done, not a fact or preference — it targets an opinion supplement instead of general memory. `harness/skills/memory/scripts/opinion_routing.py` is that rule: a deterministic classifier that requires a candidate to read as a rule **and** be about doing work, checks voice lessons out first (they belong to the style overlay — one lesson, one home), and returns a target opinion or `None`. A supplement branch in `reflect.route_candidates` writes the hit to `personal/_opinions/<name>/<slug>.md`; nothing is ever written into a coded `opinions/*.md`. The tri-lane routing (`MEMORY_REVIEW_MODE`) is untouched and orthogonal — the classifier decides the destination, the confidence ladder decides the lane, and a LOW-confidence standard still routes to its opinion.

**2 — Classification is text-shape. The signal → opinion map is retired.** The original spec routed by *where a lesson came from* — a `/review` correction to `good`, a token-audit finding to `efficient`, a PII finding to `private`. Those sources emit nothing machine-readable, and three of the four named ones (`/review`, token-audit, the PII scrubber) live in crickets rather than agentm, so keying on them means a cross-repo instrumentation project standing between the loop and any of its guards. The map is dropped as a routing mechanism. The table below survives as a reader's aid — which opinion absorbs which kind of lesson — and nothing consults it:

| Kind of lesson | Lands in |
|---|---|
| quality bars, adversarial findings, defect patterns | `good` |
| gate and battery lessons, done-criteria misses | `done` |
| cost, model-tier, and routing lessons | `efficient` |
| process, architecture, convention, and incident lessons | `how-we-engineer` |
| reversibility lessons and safety-gate near-misses | `recoverable` |
| secret, credential, and PII lessons | `private` |
| **voice and prose lessons** | **not an opinion** — the style overlay owns them, and double-capture is forbidden |

Stage 1's existing optional `source:` frontmatter field records an origin tag when a caller happens to know one (the design pass named this as a new `signal_source:` field; the build kept `source:`, which already carried exactly that meaning — one field, one fact). It is provenance and a health-check input, never a routing key, so a source that starts emitting structured records later fills that field and nothing else in the loop changes.

**3 — The anti-corruption contract (the heart of it).** Three stacked guards, each now with the mechanism it runs on:

- **Recurrence gate.** Promotion into a served supplement requires the same lesson surfacing from **two distinct sessions** — the heat-policy discipline applied to standards, since one incident is an anecdote. The lane is its own store: each entry carries a `sessions:` list, entries in one opinion's lane that pass a similarity match are one lesson, and the group promotes only when the union of its session ids reaches two. A single occurrence parks in the lane, which is exactly where reflect already wrote it.
- **Extend, never override.** The fold serves base-then-supplement with the coded base authoritative. A supplement entry that contradicts its base never promotes: it parks, and surfaces as a **proposed base change** through the cycle digest, a stable `_meta/opinion-base-proposals.json`, and the console. Applying one means a human editing `opinions/<name>.md` and committing it — overriding a shipped standard is a check-in, not a memory write. Detection is narrow by design (see call 4); the guarantee is structural, so an undetected contradiction's worst case is additive noise served beneath an authoritative base, which is the corruption ceiling the spec names and which dreaming's own dedup and compression sweep.
- **Provenance or it didn't happen.** Every supplement entry carries the session ids it was mined from, optional commit/PR/incident refs, and the existing `supersedes:` / `superseded_by:` chain. A supplement-health check reports provenance coverage and lane depth per opinion, so an unhealthy supplement is visible rather than discovered.

**4 — Cadence.** Capture is continuous and rides session-close reflection, as built. Promotion runs on dreaming's weekly cycle as one new stage — the named maintenance owner, no second mechanism. Base check-ins happen at release time by hand.

**Where Stages 2-3 run.** One new dreaming stage, `_stage_opinion_supplement()`, joining `run_dream()`'s existing hand-wired sequence the same way every stage since tidying has. It runs the recurrence gate, then the contradiction check, then composition, all deterministically — no model call, which is what makes it buildable at all: the orchestration chains fire outside the agent loop and cannot dispatch a sub-agent (`orchestration_idle.py:24`), the same blocker that stopped crystallization's distillation. It inherits staging, `dream_confirm`, the revert log, and the anomaly breaker unchanged.

#### Locked design calls (2026-07-25)

**1. The signal → opinion map is dropped; text-shape classification is the sole classifier.** *Why not instrument the sources:* three of the four are cross-repo, and the source is a weaker prior than the text anyway — a `/review` correction can be about cost or privacy as easily as quality. *Why not a hybrid* keyed on the signals that already emit structured entries (`kind: failure-incident`, session-cost): more machinery for a prior that fires on a minority of candidates and still needs the text classifier underneath. *Re-audit trigger:* revisit only if the supplement-health check shows the operator re-filing promoted entries into a different opinion often enough to be a pattern — and then as a tiebreaker on `source:`, never as a primary key.

**2. Supplement entry schema.** A lane entry keeps Stage 1's frontmatter and gains: `sessions:` (a list of `<project-slug>/<session-uuid>` ids, from `reflect._session_id_from_path` — the build threads the session id through `route_candidates` into the supplement writer, which Stage 1 did not); `source:` (optional origin tag — Stage 1's existing field, kept as-is rather than shipping a redundant `signal_source:` beside it; reconciled as-built 2026-07-25); `refs:` (a flat list of free-form commit / PR / incident refs); `promoted:` (the timestamp it entered the served file); and the existing `supersedes:` / `superseded_by:` V6-1 convention reused as-is. `status:` takes `proposed` → `promoted` → `parked` → `superseded`. *Why a flat `refs:` list rather than typed commit/incident fields:* typed fields need each source to emit them, which call 1 just established doesn't happen; a flat list is what can actually be filled today, and an entry with none is visible in the health check rather than rejected. *Re-audit trigger:* type the refs when a source starts emitting them.

**3. `kind: opinion-supplement` is registered in `kind_registry.KNOWN_KINDS`.** Stage 1 already writes this kind and it is **not** registered — the vault is at zero unrecognized kinds only because no standard has been mined yet, so the first one to land breaks that invariant. One kind covers both lane entries and the composed served file; `status:` distinguishes them. *Why not two kinds:* they are the same content at two stages of one lifecycle, and a second kind buys nothing a `status:` value doesn't. *Re-audit trigger:* none — this is a registration the build owes, and `check-kind-taxonomy` (advisory) reports it either way.

**4. Recurrence identity is same-opinion similarity at 0.85, over the lane itself.** Two entries are the same lesson when they target the same opinion and their normalized bodies match at `difflib.SequenceMatcher` ratio ≥ 0.85; the group merges into the earliest entry, accruing the union of `sessions:` and `refs:`, with the rest marked `superseded` — dedup's own merge-into-earlier mutation shape, reused rather than reimplemented, exactly as inbox triage reuses `_stage_dedup`. *Why 0.85 and not dedup's 0.92:* 0.92 is tuned for near-verbatim duplicates, and the same lesson mined from two different sessions is paraphrased, not duplicated; 0.85 is the linker's own confident band, an existing number rather than a new one. *Why the lane and not a new cross-session index:* an index is a second source of truth that can drift from the lane, and the lane is small by construction — the ~20-entry trigger below is the point at which it stops being small. *Why distinct sessions rather than entry count:* two entries from one session are one occurrence, which is the spec's own anecdote test; a Stage-1-era entry with no `sessions:` value counts as zero and can join a group without satisfying the gate. *Re-audit trigger:* 0.85 is a calibration-era number, not measured against opinion prose — revisit once real lane volume exists, tightening it if unrelated standards merge and loosening it if the gate never fires while the lane grows.

**5. Contradiction detection is narrow and high-precision; the guarantee is structural.** The check is direct normative negation on a shared anchor: the entry and a base sentence share a work-domain anchor phrase and carry opposite normative polarity (`always`/`must`/`required` against `never`/`don't`/`forbidden`). It catches the flat reversal and misses subtler conflicts on purpose. What carries the rest is composition: nothing writes into `opinions/*.md`, `opinion_resolve` returns base and supplement as separate fields, the composed file leads with a header naming the base authoritative, and a suspected contradiction never promotes at all. *Why not an LLM contradiction judge:* it cannot be dispatched from the chain, and judging whether a learned standard contradicts a shipped one is the exact place the spec says deterministic-first matters most. *Why not serve-with-a-warning instead of parking:* a warning is text the agent may weight against the base it is meant to defer to; parking removes the question. *Re-audit trigger:* the spec's own — revisit the extend-never-override ceiling only if a supplement-vs-base contradiction recurs three times or more, which is the base being wrong rather than the loop.

**6. The inbox lane is per-opinion — `personal/_opinions/<name>/`, as built — and `_opinions/` joins `dream._EXCLUDE_DIRS`.** The shared `personal/_inbox/` keeps every non-standard candidate and is untouched. *Why not the shared inbox:* the ~20-untriaged trigger is per-opinion by construction and a shared inbox cannot express it, and `inbox_triage.py`'s promote disposition would graduate a supplement to `<vault>/personal/<kind>/<slug>.md` — the wrong destination entirely. *Why exclude the directory:* `_opinions/` is in the general corpus today, so `link_improvement` would write `**Related:**` wikilinks into a served supplement — changing text the agent reads as its own standards — `tidying` would shelve a year-old standard, and general `dedup` would merge across opinions at the wrong threshold. The new stage owns this directory and no other stage touches it, mirroring `_inbox`'s own exclusion. The connectivity and browse-surface meters stop counting these entries, which is correct: they are served configuration, not notes to link. *Re-audit trigger:* revisit if a second consumer ever needs to read the lane, which would mean the exclusion is hiding it from something legitimate.

**7. Composition regenerates the served file wholly from the lane, every cycle.** `personal/_opinions/<name>.md` is a pure function of that opinion's promoted set: a fixed header naming the base authoritative, then each promoted entry as a titled section with a one-line provenance footer, ordered oldest-first. An empty set means no served file at all, so `opinion_resolve` reports `base-only` honestly. The write goes through `revert_log.record_and_apply` like every other dreaming mutation. **No resolver change:** `opinion_resolver._read_supplement` already reads exactly `<supplement_dir>/<name>.md`, so the served file sits beside its lane directory and the caller keeps resolving `<vault>/personal/_opinions` — the resolver stays stdlib-only and pure, as Stage 1's own task-3 finding established. *Why regenerate rather than append:* it is idempotent and self-healing, so a superseded, parked, or operator-rejected entry disappears on the next cycle without a second retraction mechanism, and the file is always exactly what the lane says it should be, which removes a whole drift class. *Re-audit trigger:* revisit if a served supplement grows large enough that regenerating it every cycle is wasteful, which would mean the recurrence gate is too loose.

**8. No LLM assist is built; the seam is tracked, not silent.** The spec's "the LLM assists only at MEDIUM confidence" conflated two different things: reflect's routing lane (`HIGH`/`MEDIUM`/`LOW`, which decides *where* a candidate is stored) and a classifier confidence the classifier does not have — `classify_standard_shaped` returns a target or `None`, binary. The case the spec meant is a candidate that reads as a rule about work but matches no opinion's vocabulary. It routes normally, and the unbuilt assist is named as `opinion_routing.assist_tier_available()`, returning `False` unconditionally — the same seam shape as `dream.cheap_model_tier_available()` and `dream_confirm.higher_tier_model_available()`. *Why not build it:* the chain cannot dispatch a sub-agent, and inventing a confidence scale for a regex classifier to hang a dispatch off would be fiction. *Re-audit trigger:* flip all three seams together when a chain-time model primitive exists.

**9. Promotion is confirm-gated through one supervised window, then auto-applies on a fresh operator ruling** (operator ruling, 2026-07-25). `_meta/opinion-promotion-cutover.json` stamps the stage's first run against a vault and is never overwritten — `ensure_cutover_marker()`'s shape, reused. Through the window every promotion stages as a `stage="opinion_promote"` proposal requiring `dream_confirm.confirm()`, and `opinion_promote` is deliberately **not** in `AUTO_APPLY_STAGES`. Auto-apply turns on only on an explicit later ruling recorded here as an amendment — the standing that frozenset's own docstring already requires, and the path inbox triage walked. When it does, `opinion_promote` joins `_ANOMALY_WATCHED_STAGES` in the same change: a stage that rewrites the agent's own standards is the last place to accept `link_improvement`'s cap-only-no-breaker gap. *Why not auto-apply from the first cycle:* every promotion is revertible, but the first pass over real content would self-modify before you had read a single proposal. *Why not gate it permanently:* a standards loop that needs a human every cycle stops running. *Re-audit trigger:* the ruling to widen auto-apply, once a supervised window has produced real proposals to judge it on.

**10. Supplement health lands under the `memory freshness+experience` axis.** The spec's "the dashboard's opinions family" names a family that does not exist — `health_score.FAMILY_WEIGHTS` locks exactly eight axis names, the same finding shape as the retired "FRIDAY family" reading. A `verify-opinion-supplements.sh` emits the usual `jsonl_emit.sh` health signal against that axis (the one dreaming and the auto-org meters already report to), and `console.section_opinion_supplements` renders it: per opinion, lane depth, promoted count, provenance coverage, parked and base-proposal counts. *Why not add a ninth family:* the eight are locked and a new one reweights every historical score. *Re-audit trigger:* the spec's own — if any opinion's lane exceeds roughly 20 untriaged entries, the recurrence threshold is too loose for whatever is feeding it.

**Why not the alternatives (carried forward):** a dedicated learning pipeline duplicates three shipped capture paths for zero new signal; LLM-judged auto-promotion violates deterministic-first exactly where corruption matters most; supplement-overrides-base inverts operator-voice-wins and would let two bad sessions rewrite a shipped standard.

**Carried-forward re-audit trigger:** when dreaming's consolidation starts writing live instead of only previewing, confirm it actually sweeps supplements — else schedule a lint.

**As-built (2026-07-25, [PR #380](https://github.com/alexherrero/agentm/pull/380)).** All ten locked calls are implemented against this section verbatim: `opinion_supplement.py` (a stdlib-only leaf module — same-opinion clustering at `RECURRENCE_SIMILARITY_THRESHOLD = 0.85`, promotion gated on two distinct `sessions:` ids, the narrow direct-negation contradiction check against the coded base, whole-lane composition), `dream._stage_opinion_supplement()` staging `stage="opinion_promote"` proposals through the existing propose → `dream_confirm.confirm()` → revert-log path, `kind: opinion-supplement` registered in `KNOWN_KINDS`, `_opinions/` in `dream._EXCLUDE_DIRS`, and the health surface (`_meta/opinion-supplement-health-latest.json` + `console.section_opinion_supplements` + `scripts/verify-opinion-supplements.sh`, wired into `check-all.sh` and CI). Two things stay deliberately open, exactly as call 9 and the calibration triggers require: `opinion_promote` is not in `AUTO_APPLY_STAGES` — every promotion needs an explicit confirm until a fresh operator ruling widens it, and it joins `_ANOMALY_WATCHED_STAGES` in that same change — and the two calibration numbers (0.85 similarity, the ~20-entry lane-depth warning) are unmeasured against real lane volume, which is zero today.

### Crystallization's phase-close trigger — designed and built

**Designed 2026-07-25; built 2026-07-26.** Crystallization has had a digest schema and write/read primitives since 2026-07-07, and no way to fire. The note parked it on a premise: no bounded, detectable phase-close event existed to hang a trigger on. That premise expired. Crickets [PR #214](https://github.com/alexherrero/crickets/pull/214) (`development-lifecycle 0.42.0`) shipped `agentm_bridge.py`'s sixth verb, `phase-dispatch`, and wired two call sites — `work.md` fires `post-work` after each task's commit, `release.md` fires `post-release` once the release lands. Both route through `harness_memory.phase_dispatch()` into `orchestration_phase.py`. The events crystallization was waiting for already fire today, several times per session, and now something listens on their behalf.

**The one-sentence design:** the two live phase-dispatch events are the trigger, and what they fire is *staging* — a small marker naming a session worth distilling later — because the judgment of whether a session was investigative, and the distillation that turns it into five fields, both need a model the chain cannot call.

**Why staging rather than crystallizing.** An orchestration chain fires outside the agent loop and cannot dispatch a sub-agent (`orchestration_idle.py:24`). That is the same wall the accumulate loop's LLM assist hit (call 8 there) and the same one that deferred distillation in the first place. A trigger that tried to *decide* "was this an exploration?" or *compose* the five fields at chain time would be inventing a judgment the chain has no instrument for. So the chain does the part it can do honestly and mechanically: it records that a phase closed and points at the transcript. The composing pass stays where it already is — an operator, or a future agent-side pass — and picks candidates up from a surface that now exists.

#### Locked design calls (2026-07-25)

**1. The trigger is both live phase-dispatch events: `post-work` and `post-release`** (operator ruling). No new crickets-side hook, no new session-boundary marker, no change to `work.md` or `release.md` — this consumes a seam that already ships and already fires. `post-work` is correctly scoped by construction, since only `work.md` fires it; a `/release` session earns one too, because release-time debugging (red gates, a merge conflict, a tag-reachability surprise) is real investigation worth a digest. *Why not `post-work` alone:* it would silently drop the release-session case, and both events cost the same to listen for. *Why not wait for a narrower future verb* (a hypothetical `post-bugfix-analyze` or `post-research`): the narrower event does not exist and may never; these two do, they are the only bounded phase-close events in the system, and staging is cheap and reversible enough that a mechanical session's candidate is noise an operator dismisses, not damage. *Re-audit trigger:* if a narrower investigative-session event ever ships, prefer it and retire the broad `post-work` listen.

**2. Staging is a sibling step at the subcommand level, never nested inside the reflect ladder.** `post_work_reflect()` returns early on `disabled`, `no-session`, `ambiguous-session`, `already-reflected`, and `cooldown`. Since `post-work` fires after *every* task commit and reflect renames the session's `.start` marker to `.reflected` on its first success, every later commit in that session takes the `already-reflected` path — so staging placed as a step *inside* that function would never fire on what is, after the first commit, the common path. The `post-work` and `post-release` subcommand handlers each call staging as a sibling of the existing work, and merge its outcome into the result dict under a new `crystallization` key. *Why additive under a new key rather than a restructured result:* `verify-phases.sh` already asserts on the existing top-level `"status"` values (`no-session` among them), and those assertions should keep passing untouched — the trigger is new behavior, not a change to what the dispatches already promise. *Re-audit trigger:* none; this is a placement constraint the early-return ladder imposes.

**3. Staging resolves from live `.start` markers only, and therefore runs *before* reflect.** *(Rewritten 2026-07-26 — the original version of this call shipped and was inert; see the correction below.)* Staging gets its own resolver globbing `session-id-*.start`, filtered to markers whose transcript still exists before the count (call 9), keeping the refuse-when-ambiguous rule — zero or two-or-more live markers means skip, never guess. Its position in `_main()` is part of the contract: reflect renames a session's `.start` to `.reflected` on its first success, so staging must run first or the very first task commit — the one commit that needs to stage — finds nothing.

**What the original call got wrong, and why no test caught it.** It ordered staging *after* reflect and compensated by globbing `.reflected` too, reasoning that from the second task commit onward no `.start` remains. That reasoning was locally correct and globally wrong: **`.reflected` markers accumulate for thirty days** (their own GC threshold), so counting them means two reflected sessions in a month is enough to make every later resolution see multiple competing sessions. `ambiguous-session` becomes the permanent steady state and the trigger never fires at all. It shipped that way. Every fixture — unit and end-to-end — carried one or two markers, so nothing modeled a repo with ordinary history in it, and `test_two_live_markers_is_ambiguous` asserted that ambiguity is *correct* without ever asking whether it would be *normal*. Found by dry-running the shipped trigger against this repo, which carried 111 `.reflected` markers.

*Why reorder rather than widen the glob further:* reordering removes the dependence on marker history entirely, needs no freshness window or other calibration number, and needs no crickets change. *What it costs:* `fire_count` stays at 1, since later task commits find no `.start` and skip — the "how much work did this session do" prior is gone. That is an acceptable trade, because `stage_candidate` is idempotent and the candidate itself is already written; only the counter was lost. *Why not thread the real session id through `phase-dispatch` instead* (the unambiguous fix): `orchestration_phase.py` already accepts `--session-id`, but neither `harness_memory.phase_dispatch()` nor the crickets bridge forwards one, so it would mean a cross-repo change and tighter coupling between the two repos for a case that marker resolution now handles. *Why not relax the ambiguity rule:* guessing the wrong transcript is exactly the failure `_resolve_session_marker`'s docstring refuses, and staging the wrong session is worse than staging none. *Re-audit trigger:* revisit if a host runs two genuinely concurrent live sessions per repo as the normal case — two agents sharing one checkout already happens here, though the live-transcript filter resolves it in practice when only one has a written transcript.

**4. Candidates land in `_crystallize-staging/<phase>-<session-id>.json`, and that directory joins all three exclusion lists.** Vault root, sibling to `_dream-staging/` — the same "raw material for a later pass, not corpus content" precedent. It is added to `dream._EXCLUDE_DIRS`, `vault_lint._EXCLUDE_DIRS`, and `frontmatter_validator._EXCLUDE_DIRS` in one change, which keeps `scripts/test_vault_lint.py:143-148`'s two parity assertions true rather than breaking them. *Why not a `kind:` entry in the corpus:* `kind: crystallized` is the composed digest, and a staged candidate is not a digest — writing one as an entry would put a contentless stub in the corpus and make `parse_digest` the thing that discovers it is empty. *Why exclude from all three:* a staged marker has no frontmatter conventions to validate, nothing worth linking, and no age worth shelving, so any stage that walked it would report a finding about a file that is deliberately not a note. **Corrected 2026-07-26 after mutation-testing the built trigger:** no walker reaches it today regardless — all three match `*.md` only while candidates are `*.json`, and two of the three (`vault_lint`, `frontmatter_validator`) scan `personal/` and `projects/` rather than the vault root. The exclusion is therefore defense-in-depth against a later change to either of those facts, not a live hazard; the original phrasing here overstated it. It is worth keeping precisely because both facts are incidental rather than guaranteed, and `test_vault_lint.py` now pins the membership so the guarantee cannot silently lapse. *Re-audit trigger:* revisit if a second consumer needs to read the staging directory, which would mean the exclusion is hiding it from something legitimate.

**5. Staging is idempotent on `(phase, session-id)` with no cooldown.** Re-firing refreshes a `last_fired` timestamp and increments `fire_count`; it never writes a second candidate for the same session. A pending cap (`_MAX_PENDING_CANDIDATES`, 50) skips staging when the directory is already that deep, recording the skip rather than growing without bound. *Why no cooldown, unlike every sibling chain:* a cooldown exists to stop expensive repeated work, and this write is a few hundred bytes — gating it on the shared `phase_reflect` clock would silently drop candidates for whole sessions, losing exactly the signal the trigger exists to catch, and gating it on a new clock buys nothing idempotence does not already give. *Why `fire_count` rather than one-shot:* `post-work` firing once per task commit makes the count a free record of how much work the session did, which is a real prior for whether it is worth distilling. *Re-audit trigger:* 50 is a calibration-era number with no measured pending volume behind it; revisit once real candidates accumulate, and treat a cap that trips as evidence the pickup surface is not being read rather than as a bound to raise.

**6. Candidates surface as a count derived from the staging directory itself.** `session_brief.py` gains a pending-candidate count beside `count_parked` and `count_needs_your_eye`, and `console.py` gains a matching section — the two surfaces that already carry "something waits for you." The count comes from globbing `_crystallize-staging/*.json`. *Why not append to `_meta/needs-your-eye.json`, the channel that already feeds both surfaces:* `inbox_triage.py:791` overwrites that file wholesale on every run, so an appended item would be silently clobbered by the next dreaming cycle. `count_parked`'s glob-the-directory shape is clobber-proof and needs no writer coordination; `count_needs_your_eye`'s pointer-file shape is neither. *Re-audit trigger:* if the needs-your-eye pointer ever becomes multi-writer by design, fold this count into it and drop the separate glob.

**7. The deferred judgment and distillation get one named seam: `crystallize.exploration_judge_available()`, returning `False` unconditionally.** It covers both halves — whether a staged session merits a digest, and what the five field values are — because both need the same absent instrument, and two seams for one missing capability is two things to forget to flip. This is the fourth seam of exactly this shape, joining `opinion_routing.assist_tier_available()`, `dream.cheap_model_tier_available()`, and `dream_confirm.higher_tier_model_available()`. *Why name it rather than leave the gap in prose:* the accumulate loop's call 8 established that an unbuilt assist should be a callable returning `False` — it makes the gap greppable and gives the eventual build one place to change. *Why not a heuristic in the meantime* (transcript length, `fire_count`, files-touched): it would encode a guess about what makes a session investigative as though it were a measurement, and a wrong filter that runs silently is worse than an honest unfiltered list an operator skims. *Re-audit trigger:* flip all four seams together when a chain-time model primitive exists.

**8. A picked-up or dismissed candidate is deleted, not archived.** Composing a digest through `crystallize.py write` and dismissing a candidate both end the same way: the marker file is removed. *Why no archive:* the marker holds no content — a session id, a transcript path, a timestamp, a count — so once a digest exists or the operator has passed, there is nothing worth retaining, and an archive directory would accumulate stubs that mean nothing to a later reader. This is deliberately unlike `_dream-staging/`, whose proposals carry real proposed content that a revert or an audit may need to read back. *Re-audit trigger:* revisit if candidates ever carry distilled content, which would make deletion lossy.

**9. The single-marker rule was unsatisfiable, and the cause was a broken transcript path — fixed separately, before this trigger builds** (operator ruling — scope widened to fix the defect rather than work around it). The rule calls 2-3 depend on could not be met at all. `.harness/` held **200 `session-id-*.start` markers and zero `.reflected`** across seven weeks, so `_resolve_session_marker()` returned `ambiguous-session` unconditionally.

The reason was not marker churn or concurrent sessions. Both memory hooks computed the transcript path with an extra leading hyphen, so every marker ever written pointed at a directory that does not exist — and the orphan sweeper, which skips any marker whose transcript it cannot find, skipped all of them on every pass instead of ever clearing one. `post_work_reflect()` had therefore never once succeeded, nor had the Stop hook, which meant crickets [PR #214](https://github.com/alexherrero/crickets/pull/214)'s stated purpose — reflection on a host with no Stop hook — did not hold either. That fix landed on its own in [PR #385](https://github.com/alexherrero/agentm/pull/385); the 2026-07-26 amendment below carries the full account, including why a full green gate battery never caught it.

What remains locked here is the sweep this trigger depends on. The sweeper **deletes** a `.start` marker whose transcript cannot be found — past the idle threshold only, so a live session whose transcript has not been written yet is never destroyed — and any marker that keeps failing to reflect past a hard ceiling, reusing the existing 30-day `.reflected` GC threshold rather than inventing a number. Marker resolution then **filters to markers whose transcript still exists** before applying the exactly-one rule, so correctness does not depend on a sweep having run recently. *Why delete rather than reflect:* a transcript that cannot be found can never be reflected from, so the marker is not pending work, it is a dead pointer. *Why the age gate licenses the delete rather than the missing transcript alone:* a fresh marker's transcript may simply not exist yet. *Why fix it rather than work around it:* the trigger's entire value is a transcript pointer, and building on a rule that resolves `ambiguous-session` forever would ship a feature whose only observable behavior is reporting that it skipped. *Re-audit trigger:* if markers with resolvable transcripts start accumulating again, reflection is failing for a reason none of this found.

The live-transcript filter stays load-bearing after the 2026-08-01 payload change, but it now guards a smaller class. Reading `transcript_path` off the payload stops the hooks from *minting* dead pointers; it does not make an existing pointer immortal, since a transcript can still be deleted, rotated, or moved between the marker's write and the sweep that reads it. The filter is what keeps that ordinary decay from manufacturing false ambiguity, and it stays.

**Verification lands in `verify-phases.sh`, not a new gate.** That script already exercises both dispatches in dry-run across a vault-resident and a vault-less pass, and already covers the session-marker scenarios call 3 turns on. Extending it keeps the battery at its post-consolidation count instead of adding a 35th gate for behavior the existing phase gate is precisely scoped to.

**No crickets change.** This consumes `phase-dispatch` exactly as shipped; `work.md` and `release.md` keep their current text and their always-exit-0 contract. The one crickets-side obligation is prose: any place its `development-lifecycle` design describes what `post-work`/`post-release` *do* now names a second listener, so that description does not go stale.

**As-built (2026-07-26).** All nine locked calls are implemented against this section verbatim. `crystallize.py` gains the staging primitives it owns — `STAGING_DIRNAME`, `_MAX_PENDING_CANDIDATES = 50`, `stage_candidate()` (idempotent on `(phase, session_id)`, refreshing `last_fired` and incrementing `fire_count` on re-fire), `list_candidates()`, `drop_candidate()` (delete, never archive — call 8), `count_pending_candidates()`, and `exploration_judge_available()` returning `False` (call 7). `orchestration_phase.py` gains `_resolve_transcript_for_staging()` — resolving from live `.start` markers only, filtered before the exactly-one rule (call 3 as rewritten; the original `.reflected` fallback shipped inert, see the amendment log) — and `stage_crystallization_candidate()`, called as a sibling step from `_main()`'s `post-work` and `post-release` branches, ahead of reflect so the marker still exists, merged under a new `"crystallization"` result key (call 2) with no cooldown (call 5). `enable_crystallization_staging` joins `auto_orchestration.DEFAULT_CONFIG`, default `True`. `_crystallize-staging` joins `dream._EXCLUDE_DIRS`, `vault_lint._EXCLUDE_DIRS`, and `frontmatter_validator._EXCLUDE_DIRS` in one change (call 4), keeping `scripts/test_vault_lint.py`'s parity assertions true. `session_brief.py` and `console.py` each gain a directory-globbed pending count beside their existing push-surface signals (call 6). Tested by `scripts/test_crystallize_staging.py` (28 tests: staging primitives, the tolerant resolver's dead/live/ambiguous cases, and the dispatcher's disabled/no-session/staged/refreshed/capped/dry-run/ambiguous states) and a new section in `scripts/verify-phases.sh` (10 checks) proving the sibling-step wiring end-to-end through the real CLI — including the exact scenario call 2 exists to prevent: staging still fires once reflect has renamed a session's marker to `.reflected`. No new gate; verification rides the existing phase-lifecycle check. `check-all.sh`: 34/34 green, no new row.

Experience keeps working on a bare agentm.
