# Named plans (multi-plan state)

> [!NOTE]
> **Status: implemented** (2026-06-13, updated 2026-09-22). The multi-plan-state substrate — the round-trip lock, `resolve_active_plan`, the `check-multi-plan-naming` gate — ships in `main`; crickets' development-lifecycle plugin writes the `.harness/active-plan` marker this page's reader consumes. Build history below has the full rollout, through plan 15's retirement of the vault fallback.

Named plans let the harness hold more than one active plan in the same shared vault. Each named plan lives in its own `PLAN-<name>.md` with a matching `progress-<name>.md`, alongside the unnamed pair a solo session already uses. A resolution model then binds every session to exactly one plan — the one it owns. This is the substrate the coordinator-directed worker team stands on: give each worker its own plan file, and the team never collides on harness state.

## Why this exists

Through V5-0, harness state assumed **one active plan per project**: `read_state_file` / `write_state_file` resolved a fixed `PLAN.md` and `progress.md` under the project's `_harness/`, and every phase spec, hook, and the `doctor` skill looked for *the* `PLAN.md`. That is fine for a solo session, but V5's direction is **concurrent agents — one session per worker** — and several workers driving one singleton plan file would serialize the whole team onto one document.

Named plans remove that bottleneck. A plan can be named — `PLAN-foo.md` with its own `progress-foo.md` — so two workers touch **different files** and never contend on the same document. The contract is strictly **additive**: the unnamed `PLAN.md` / `progress.md` path is unchanged, so a solo session keeps working exactly as before. There is no data migration.

This page is the agentm **substrate** slice only. The behavioral half — the `/work <named-plan>` phase argument, the writer that appends `progress-<name>.md`, the staging UX that emits a named plan — lives in the companion crickets **development-lifecycle** plugin (the V5-unbundling boundary: agentm owns the durable state, crickets owns the phase loop). See [The agentm/crickets seam](#the-agentmcrickets-seam) below.

## The naming contract

Named plan files are **flat at the repo-local `.harness/` root** (agentm-vault plan 15 retired the vault-side `_harness/` this used to also apply to) — not a per-plan subdirectory, not a generalized `queued-plans/` staging tier (that staging tier is a separate, crickets-side concept).

| File | Style | Written by |
|---|---|---|
| `PLAN.md` (unnamed) | replace (content-hash CAS) | the singleton path — unchanged, back-compatible |
| `PLAN-<name>.md` | replace (content-hash CAS) | the named-plan path |
| `progress.md` (unnamed) | append-only | the singleton path — unchanged |
| `progress-<name>.md` | append-only | the named-plan writer (crickets-side) |

A task's plan takes a third shape (agentm-vault plan 09): `tasks/<slug>/plan.md`, with its `progress.md` and `tracker.md` beside it in the same directory, all three addressed by absolute path rather than a bare filename under the repo-local `.harness/`. It resolves only on a synced backend, since a device-local `.harness/` has no project directory to hold a `tasks/` tree. Within a slug, a task at `tasks/<slug>/plan.md` is tried first, and the flat `PLAN-<slug>.md` pair is the fallback — a second place a slug can resolve, alongside the flat naming contract above.

### Optional YAML frontmatter on plan files

Plan files may carry a YAML frontmatter block (delimited by `---`) with two optional coordinator fields introduced in V5-11:

| Field | Type | Purpose |
|---|---|---|
| `depends_on` | list[string] | Slugs of plans that must complete before this one is ready to start. Used by `scripts/readiness.py` for dependency-readiness checks and `scripts/merge_order.py` for topo-sort ordering. |
| `touches` | list[string] | Glob patterns of files this plan modifies (e.g. `scripts/foo*.py`, `wiki/reference/*.md`). Used by `scripts/readiness.py` to detect safe-to-run-together overlap. Plans **without** `touches:` are loudly degraded by the readiness checker — never silently assumed safe to run concurrently. |

Both fields are purely additive — absent fields mean "no declared deps" and "no declared file scope" respectively. A solo-session plan without frontmatter is unchanged by this convention.

The replace-vs-append split is what the design leans on. `PLAN-*` files are **replace-style** and go through the vault-write protocol's content-hash compare-and-swap, exactly like the unnamed `PLAN.md`. `progress-*` files are **append-only** — they are never CAS-replaced, because two workers appending to one progress file merges naturally through Drive's append handling, while a replace-style write of a progress file would reintroduce the contention this whole design avoids. The append discipline for `progress-<name>.md` is enforced where the *writer* lives (crickets-side); this substrate slice locks the round-trip read contract and documents the append contract so the writer cannot drift.

## Why this is a naming convention, not a dispatcher rewrite

The state resolver is already filename-agnostic. `vault_state_path(resolution, filename)` does pure path construction, and `safe_write_replace_style` runs its content-hash CAS on an arbitrary path — neither keys on the literal string `"PLAN.md"`. Named plans fall out of that resolver for free: a named file is just a different `filename` argument threading through the same path construction and the same atomic-write-under-mutex machinery (see [Vault write protocol](Vault-Write-Protocol)).

What the substrate work adds is not new resolution logic but two guards that lock the contract: a test suite that proves the round-trip — a `PLAN-foo.md` resolves under the repo-local `.harness/`, named content reads and writes back, content-hash CAS raises on a stale hash exactly as it does for the singleton, and the conflict janitor flags `PLAN-foo (conflicted copy …).md` — and the `check-multi-plan-naming` gate (CI gate #13), which asserts the resolver still exposes the named-plan entry points (`resolve_active_plan` and `state_dir` — `harness_state_dir` retired under agentm-vault plan 15) and that no curated harness doc silently reasserts a singleton. Both are locked by dedicated test suites; see the shipped-surfaces table [below](#what-has-shipped-so-far) for the files and counts.

If any of that work surfaces a *caller* somewhere that hard-codes `"PLAN.md"` (the resolver itself is clean; a caller might not be), the fix is to close it minimally.

## Binding a session to its plan — `resolve_active_plan`

A worker must end up bound to **exactly one** plan, and a mis-binding (a worker silently working the wrong plan) is the foot-gun this design most wants to prevent. The [`resolve_active_plan`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py) helper makes the binding explicit with a strict precedence:

```
explicit argument
  → worktree-local .harness/active-plan marker
    → legacy PLAN.md / progress.md
```

It returns the resolved plan filename and its matching progress filename. The marker pattern mirrors the existing `.project-mode` repo-local marker (reachable on disk without consulting the vault).

The rule that matters here: `resolve_active_plan` errors loudly and never silently falls back to the singleton. When `.harness/active-plan` exists but names a plan whose `PLAN-<name>.md` is absent, empty, or ambiguous, it raises rather than quietly degrading to `PLAN.md`. A silent fallback there is exactly how a worker would end up editing the wrong plan; raising turns a mis-binding into an immediate, observable failure. Only the unset case — no argument and no marker — resolves to the legacy singleton, which is the intended back-compat path.

`resolve_active_plan` and its four helpers (`_read_active_plan_marker`, `_normalize_plan_name`, `_is_safe_plan_slug`, `_plan_pair`), plus a dedicated `ActivePlanError`, live in [`scripts/harness_memory.py`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py). What is locked: the precedence order above, an explicit-arg traversal guard (`ValueError` on a slug that is not a single path component), and `ActivePlanError` on every present-but-unresolvable marker (blank, malformed, traversal, or naming an absent/empty plan). This helper is the reader half of the contract; the marker writer (the crickets worktree-spawn helper) shipped in development-lifecycle v3.7.0.

`resolve_active_plan` returns an `ActivePlan` (agentm-vault plan 09) rather than a bare tuple. It still unpacks and compares as the `(plan, progress)` pair every existing caller reads, so nothing that destructures it breaks. It also carries `.tracker` (the tracker file beside the pair), `.layout` (`"local"` for the repo-local `.harness/`-relative names above — renamed from `"flat"` when agentm-vault plan 15 retired the vault's `_harness/` fallback — and `"task"` for the absolute paths a task directory resolves to), and `.slug`. Within a slug, a task at `tasks/<slug>/plan.md` is tried first and the flat `PLAN-<slug>.md` pair is the fallback — see [The naming contract](#the-naming-contract) above. `active_plan_paths(resolution, plan_arg=...)` composes the full `(plan, progress, tracker)` paths in one call: it joins a flat name onto the resolved repo-local `.harness/` and leaves a task's already-absolute paths alone.

**Placement, lookup by either form, and the bare-call refusal (agentm-vault plan 10, task 7; the directory-existence check itself retired under plan 15, task 2).** On a project that keeps its plans in numbered tasks — every project on a synced backend, unconditionally, since plan 15 stopped consulting whether a `_harness/` directory happened to still exist on disk — a slug that names no task is **placed** rather than left unresolved: [`_placed_task`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L1462) composes `tasks/NNN-<verb-slug>/` with the next free three-digit number and writes nothing — `/plan` writes the plan there, and the directory is what makes the task exist, so a plan written the day after the move doesn't land back in a directory that no longer exists. A task's name is its directory name, number included, and [`_resolve_task_dir`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L1381) (via [`_match_task_dirs`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L1367)) finds it by either form — the full `042-build-the-brief`, or the verb slug alone, `build-the-brief` — with an exact directory name short-circuiting so it's never ambiguous with a numbered one. Two tasks sharing a verb slug is a real ambiguity, not a guess the resolver makes for you: it raises `ActivePlanError` naming both, exit `2` at the CLI. A project reads this way whenever [`_keeps_plans_in_tasks`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L1450) is true — which, since plan 15, is simply "a synced backend resolves" (`_state_backend_target(resolution) is not None`), nothing on disk consulted; a repo with no vault and a `.project-mode=local` opt-out are the only cases left that keep the repo-local flat-pair behavior.

Because the helper is a Python function and phase specs shell out from bash, a thin [`resolve-active-plan` CLI verb](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L2243) wraps it: it emits the resolved `<plan_path>\t<progress_path>` pair on stdout so the crickets development-lifecycle phase specs can target named plans without reimplementing precedence. `--with-tracker` appends the tracker path as a third tab-separated field, for a caller that also wants `tracker.md` (or `tracker-<name>.md`) without re-deriving it. Exit codes mirror the reader's stance — `0` resolved, `1` a repo-local pair with no project root to join it to (unreachable in practice: `resolve_project` always sets one), `2` loud on a dangling `.harness/active-plan` marker, an unsafe slug, or two tasks sharing one verb slug, never a silent singleton fallback, and `4` — nothing on stdout, one line on stderr — when a bare call names no plan on a project that keeps its plans in numbered tasks: it has no singleton `PLAN.md` to answer with, so [`resolve_active_plan` raises `TaskNameRequired`](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L1292) instead and the [CLI dispatch](https://github.com/alexherrero/agentm/blob/main/scripts/harness_memory.py#L2441) maps it to exit 4. [`process_seam.py`'s `state_path` shim](https://github.com/alexherrero/agentm/blob/main/scripts/process_seam.py#L226) answers a bare `state-path` call the same way — see [Process seam](Process-Seam) for that side of the contract. It is read-only, and it is a consumption bridge for the crickets side rather than one of the substrate's own numbered tasks. See the shipped-surfaces table [below](#what-has-shipped-so-far) for both files and their test counts.

`resolve_active_plan` is a **reader** of the marker. The marker is *written* by component (2)'s worktree-spawn helper (crickets development-lifecycle' `spawn_worker.py`, shipped v3.7.0, 2026-06-13) — a separate plan on the crickets side. That split follows the architecture (see the seam below); the reader's own tests create the marker by hand.

## The agentm/crickets seam

This substrate and its behavioral half split along a real architectural seam:

| Owned by agentm (this slice) | Owned by crickets (sibling plan) |
|---|---|
| the named-plan resolver contract + its test lock | the `/work <named-plan>` phase argument |
| `resolve_active_plan` (reads `.harness/active-plan`) | the `progress-<name>.md` append writer |

| `list_plan_files(harness_dir)` public function + `list-plans` CLI verb ✅ (shipped, V5-5 task 3) | the session-start hook callers (hooks delegate *to* this verb) |
| the `queue_status_lite` read logic | the `/queue-status-lite` command surface |
| the `check-multi-plan-naming` gate | `/plan` + `/design sequence` emitting `PLAN-<name>.md` |
| named-plan-aware session-start hooks + `doctor` ✅ (shipped, task 5; hooks updated V5-5 task 3) | the two-tier staging → activation UX |

**Crickets-side status (2026-06-12):** the named-plan **writers** shipped — `/work`, `/plan`, and `/review` take a uniform `--name <slug>` flag (the right column's first three rows), resolving the pair through a `resolve_plan.py` bridge that shells to the `resolve-active-plan` verb rather than reimplementing precedence. Still crickets-side pending: the `/queue-status-lite` command surface, `/design sequence` emitting `PLAN-<name>.md`, and the two-tier staging → activation UX.

The seam point: this plan's `resolve_active_plan` **reads** `.harness/active-plan`; component (2)'s worktree-spawn helper **writes** it. Because a single `/work` session is single-repo and reads only its own repo's `.harness/`, the split is forced by the architecture — the substrate can be built and verified independently, but an end-to-end "a worker runs `/work --name foo`" demo needs both the crickets sibling plan (**shipped 2026-06-12**) and the marker writer (**shipped 2026-06-13**). Both are now in place.

## What this slice does not do

This slice stops at a deliberate boundary:

- It creates **no worktrees itself** — this slice ships only the *reader* of the `.harness/active-plan` marker. The writer (originally `spawn_worker.py`, now crickets' `worktree_marker.py` binding a host-created worktree) lives entirely on the crickets side of the seam.
- It ships **no integration / merge command** — combining two workers' output is a later plan.
- It defines **no role agent-defs** (researcher / project-manager / tech-lead / worker) — also later.
- It does **not** retire the `worktrees-never-auto` convention — that changes behavior for concurrent sessions and lands with the worktree component, not here.
- It does **not** arbitrate claims or leases between workers. The read-model ([Queue status lite](Queue-Status-Lite)) is informational only; **the human is the arbiter**.

Locked by the new `TaskPlacementAndLookup` class in [`scripts/test_resolve_active_plan.py`](https://github.com/alexherrero/agentm/blob/main/scripts/test_resolve_active_plan.py) (18 tests) and 2 new methods in [`scripts/test_process_seam.py`](https://github.com/alexherrero/agentm/blob/main/scripts/test_process_seam.py). The data half — the migration that actually dissolves `_harness/` into this shape — is [Run the projects migration](Run-The-Projects-Migration).

**Plan 15 update (2026-09-22) — the retirement, task 2.** With the projects migration long since run against every real project, `_keeps_plans_in_tasks` stopped asking whether a `_harness/` directory happened to still exist and now answers purely from whether a synced backend resolves — a writer that ever recreated a stray `_harness/` on a migrated project could otherwise silently turn a bare call back into the retired singleton, which is exactly the failure mode this closes. `ActivePlan.layout` is renamed `"flat"` → `"local"` (the task-layout label, `"task"`, is unchanged), since the flat pair now only ever means the repo-local `.harness/`, never a vault one. `resolve-active-plan`'s exit code `1` — "a repo-local pair with no project root to join it to" — was already unreachable in practice before this change and stays so; it is no longer documented as the vault's "no resolvable `_harness/`" case, because that case no longer exists. `read_state_file` / `write_state_file` (the flat-filename-only readers/writers this page's "Why this exists" section describes as V5-0's original shape) are retired outright, replaced by `read_machine_file` / `write_machine_file` (a project's `desk/`, keyed by filename, not a plan pair) and the new `append-progress` CLI verb, which appends to whichever progress log `resolve_active_plan` answers — a task's or the repo-local pair's. See [CI gates](CI-Gates) for `check-no-harness-paths`, the gate that now keeps the retired directory's name out of the code entirely.
